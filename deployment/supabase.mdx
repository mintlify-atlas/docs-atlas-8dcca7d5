Supabase is the primary data layer for AI Surfer, providing a managed PostgreSQL database, row-level security (RLS), Supabase Auth for email-based user accounts, and Deno-based Edge Functions for server-side event processing. Every lead captured by the Sales Agent, every audit queued by the Wave Audit, and every member account is stored in Supabase. The platform uses two Supabase client configurations: a browser client with `persistSession: true` for authenticated frontend users, and a server-side client with `persistSession: false, autoRefreshToken: false` in each Express API handler to avoid leaking session state across requests.

## Auth Setup

AI Surfer uses **Supabase Auth** with the email/password provider. Authentication is handled by the browser client in `src/lib/supabase.ts`:

```typescript src/lib/supabase.ts
import { createClient } from "@supabase/supabase-js";

export const supabase = createClient(
  supabaseUrl,
  supabaseAnonKey,
  {
    auth: {
      persistSession: true,
      autoRefreshToken: true,
      detectSessionInUrl: true,
    },
  }
);
```

After sign-in, the Members Dashboard and product pages check the user's `app_metadata.role` claim to determine access level:

```typescript
// Admin/owner check used in MembersDashboard and MemberProduct
if (user.app_metadata?.role === "owner") {
  // Show owner-only controls
}
```

The `owner` role must be set directly in Supabase Auth's `app_metadata` — it is not derived from the `users.tier` column and cannot be self-assigned by a user.

<Note>
  A trigger function (`handle_new_auth_user`) automatically provisions a row in `public.users` when a new `auth.users` record is created. New users always receive `tier: 'free'` and `status: 'active'` unless Stripe has already upgraded them.
</Note>

## Server-Side Client Configuration

Every Express API handler that writes to Supabase creates a short-lived client with sessions disabled:

```typescript src/server/api/aiFinLeads.ts
function getSupabaseClient() {
  const url = process.env.SUPABASE_URL || process.env.VITE_SUPABASE_URL;
  const anonKey = process.env.SUPABASE_ANON_KEY || process.env.VITE_SUPABASE_ANON_KEY;

  if (!url || !anonKey) return null;
  return createClient(url, anonKey, {
    auth: { persistSession: false, autoRefreshToken: false },
  });
}
```

<Note>
  `persistSession: false` and `autoRefreshToken: false` prevent the Supabase client from attempting to read or write cookies/localStorage in a Node.js environment. Every API handler instantiates its own client rather than sharing a singleton, which avoids session state leaking between concurrent requests.
</Note>

## Supabase Edge Functions

Two Edge Functions live in `supabase/functions/` and are deployed to Supabase's Deno runtime independently of the Express server.

<Tabs>
  <Tab title="stripe-webhook">
    Handles `checkout.session.completed` events from Stripe. When a customer completes a checkout, the function reads the `tier` value from the session metadata and updates the corresponding row in `public.users`.

    ```typescript supabase/functions/stripe-webhook/index.ts
    import { serve } from "https://deno.land/std/http/server.ts";
    import Stripe from "https://esm.sh/stripe?target=deno";
    import { createClient } from "https://esm.sh/@supabase/supabase-js@2";

    const stripe = new Stripe(Deno.env.get("STRIPE_SECRET_KEY")!, {
      apiVersion: "2023-10-16",
    });

    const supabase = createClient(
      Deno.env.get("SUPABASE_URL")!,
      Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")!
    );

    serve(async (req) => {
      const signature = req.headers.get("stripe-signature")!;
      const body = await req.text();

      const event = stripe.webhooks.constructEvent(
        body,
        signature,
        Deno.env.get("STRIPE_WEBHOOK_SECRET")!
      );

      if (event.type === "checkout.session.completed") {
        const session = event.data.object;
        const email = session.customer_details?.email;
        const tier = session.metadata?.tier || "bronze";

        if (email) {
          await supabase.from("users").update({ tier }).eq("email", email);
        }
      }

      return new Response("ok", { status: 200 });
    });
    ```

    This function uses the **service-role key** (`SUPABASE_SERVICE_ROLE_KEY`) because it needs to bypass RLS to update the `users` table. The service-role key is only available inside the Edge Function runtime and is never exposed to the browser.
  </Tab>
  <Tab title="new-client">
    Triggered after a successful Stripe payment to provision a new client: create the project record, and send a welcome email. The flow is:

    ```
    Client Pays
        ↓
    Stripe Webhook
        ↓
    Supabase Edge Function
        ↓
    Create Client
        ↓
    Send Welcome Email
        ↓
    Create Project
    ```

    Deploy this function from the Supabase CLI:

    ```bash Terminal
    supabase functions deploy new-client
    ```
  </Tab>
</Tabs>

## Environment Variables

<CardGroup cols={2}>
  <Card title="Frontend Variables (VITE_*)" icon="browser">
    Used by the browser Supabase client. Safe to expose — use the anon/publishable key only.
  </Card>
  <Card title="Server Variables" icon="server">
    Used by Express API handlers. Set these in your server environment, never in `VITE_*` vars.
  </Card>
</CardGroup>

| Variable | Context | Description |
|---|---|---|
| `VITE_SUPABASE_URL` | Browser | Public Supabase project URL |
| `VITE_SUPABASE_ANON_KEY` | Browser | Supabase anon/publishable key |
| `SUPABASE_URL` | Server | Same project URL, used by Express handlers |
| `SUPABASE_ANON_KEY` | Server | Anon key for Express handlers (RLS enforced) |

<Warning>
  **Never use the Supabase service-role key in a `VITE_*` variable.** The service-role key bypasses all row-level security policies and has full read/write access to your database. It should only appear in Supabase Edge Function secrets (`SUPABASE_SERVICE_ROLE_KEY`) or in secure server-side environments — never in any variable that gets bundled into browser JavaScript.
</Warning>

## Running Migrations

Apply the schema migrations to your Supabase project using the Supabase CLI:

<Steps>
  <Step title="Link your project">
    ```bash Terminal
    supabase link --project-ref mkgnyarwiscttobnytin
    ```
  </Step>
  <Step title="Push all migrations">
    ```bash Terminal
    supabase db push
    ```

    This applies all files in `supabase/migrations/` in chronological order, creating the `wave_audit_leads`, `ai_fin_audits`, `ai_fin_handoffs`, `ai_fin_follow_ups`, `ai_fin_onboarding`, and `users` tables along with their RLS policies and indexes.
  </Step>
  <Step title="Deploy Edge Functions">
    ```bash Terminal
    supabase functions deploy stripe-webhook
    supabase functions deploy new-client
    ```
  </Step>
  <Step title="Set Edge Function secrets">
    ```bash Terminal
    supabase secrets set STRIPE_SECRET_KEY=sk_live_...
    supabase secrets set STRIPE_WEBHOOK_SECRET=whsec_...
    supabase secrets set SUPABASE_SERVICE_ROLE_KEY=...
    ```
  </Step>
</Steps>

<Info>
  For the full list of all environment variables — including OpenAI, Stripe, and Cloudflare credentials — see the [Environment Setup](/environment-setup) reference page.
</Info>
